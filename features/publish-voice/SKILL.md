# 출간용 문체 (publish-voice)

사용자가 공개할 글을 쓰거나 다듬으려 할 때 이 파일을 따라요. 켜는 스위치는 없고, 대화에서 니즈가 보이면 바로 시작해요.

명령은 이 파일 옆의 `bin/voice.ts`예요: `bun <이 폴더>/bin/voice.ts <명령>`. 결과는 `~/.dotz/custom/publish-voice/` 아래에 사용자별로 쌓여요(`DOTZ_DIR`이 있으면 그 아래). 이 코드는 모델을 부르지 않고 감시, 예약, 폴링도 없어요. 비용은 글을 쓰는 턴에만 생겨요. 종료 코드: 0 완료, 3 막힘이나 사용자에게 물을 것, 1 실행 오류.

## 언제 쓰나

| 요청 | 발동 | mode |
|---|---|---|
| 블로그 글 써 줘 | 예 | new |
| 이 글 칼럼으로 다듬어 줘 | 예 | edit |
| 뉴스레터 초안 잡아 줘 | 예 | new |
| 책 원고 3장 이어서 써 줘 | 예 | new |
| 내 말투로 스레드 올릴 글 써 줘 | 예 | new |
| 이 사람처럼 써 줘 (대상 지정) | 예 | new, other |
| 공지문 다듬어 줘 | 예 | edit |
| 이 메일 답장 써 줘 | 아니요 | |
| 카톡 뭐라고 답할까 | 아니요 | |
| README 고쳐 줘, API 문서 써 줘 | 아니요 | |

메일·메신저 답장은 reply-drafts 몫이에요. 판단은 이 표를 기준으로 직접 해요. `route --request "<요청 원문>" [--draft <파일>]`이 `{ fire, mode, cell, other, basis, ask?, inNeeds? }`를 내지만 참고값이에요. `fire`가 false여도 표에 맞으면 이어가요.

## 시작

`status`의 마지막 `다음:` 줄이 할 일이에요. 어디서 멈췄든 이 줄부터 이어가요. `준비됐어요`면 아무것도 묻지 않고 글쓰기로 가요.

## 세팅

처음이면 요청에 없는 것만 한 번에 짧게 물어요: 어떤 글인지(용도, 길이), 누가 읽는지, 분석할 글이 어디 있는지. 요청에 있는 건 묻지 않아요. 사용자에게 설정 파일을 만들게 하지 않아요.

1. `needs add --request "<요청 말>" --audience "<독자>"`로 칸을 정해요(`--cell <칸>`도 돼요). 니즈에 없는 칸은 만들지 않아요. 칸은 길이(short 500자 미만, medium 500~3,000자, long 3,000자 이상)와 용도(story, opinion, guide)의 곱이에요.
2. `discover`로 읽을 수 있는 곳을 봐요. 파일 이름만 세고 내용은 열지 않아요.
3. 범위를 정해요: `scope add --type folder|file|url|blog|mail|messages [--path|--url|--account <값>] [--limit N]`. 범위 끝이 없는 대상은 받지 않아요(blog, mail, messages는 `--limit`이 끝이고 기본 50, 200, 500이에요). `messages`는 dotz로 보낸 메시지만이라 다른 곳에서는 비어 있어요.

## 읽기

- 읽기 전에 어디서 어디까지 읽을지 말해요. `scope add`가 찍는 문장을 그대로 쓰면 돼요. 말한 뒤 허락을 기다리지 않고 바로 `analyze`를 돌려요.
- 사용자가 빼 달라거나 바꾸면 따라요. `scope remove <id>` 뒤 다시 `analyze`해요. 범위가 모두 빠진 목소리는 저장된 글이 지워지고 고친 글만 남아요. 읽지 못한 곳은 `status`의 `다음:`이 알려요. 말한 범위 밖은 읽지 않아요. `analyze`는 `scope.json`에 적힌 곳만 읽고 끝에 출처별 건수를 찍어요.
- 종료 코드 3은 회사 메일이나 민감한 곳이에요. 찍힌 문장으로 사용자에게 묻고, 허락하면 같은 명령에 `--asked`를 붙여요. 묻기 전에는 읽지 않아요. 카카오톡과 웹메일 사이트는 대상이 아니에요.
- 폴더 안에서 경로가 민감해 보이는 파일(인사, 급여 등)은 빼고 읽어요. `scope add`가 찍는 읽을 개수와 뺀 개수를 말하고, 넣으려면 먼저 묻고 `--asked`로 다시 실행해요. 폴더는 파일 5,000개, 깊이 8단계까지예요.
- 다른 사람 글은 `--kind other --voice <이름>`으로 줘요. 통계와 해시만 남고 원문은 저장하지 않아요. `learn`에는 `--before`가 꼭 필요하고 고침 기록에 문장은 남지 않아요.
- 글을 더하면 범위가 달라지니 다시 말하고 `analyze`해요. 칸만 늘릴 때는 다시 읽지 않고 저장된 측정값으로 계산돼요.

## 글쓰기

1. `brief --request "<요청 원문>" [--draft <파일>] [--material <파일>] [--voice <이름>] [--cell <칸>]`을 돌려요. 칸을 고르고 글쓰기 자료를 찍어요. 칸이 정해지지 않으면 찍힌 질문을 그대로 물어요.
2. 자료대로 써요.
   - 첫 줄에 `근거 없음`이 있으면 사용자에게 그 칸은 그 사람 글이 부족하다고 알리고, 문체 값 없이 요청과 재료만 따라요. 다른 칸의 값을 빌리지 않고, 짧은 메시지 말투를 긴 글로 늘리지 않아요.
   - 수치는 문체로만 따르고 글에 적지 않아요. 예문의 내용과 문장은 옮기지 않아요.
   - 다듬기는 초안에 없는 사실, 숫자, 이름을 넣지 않고 뜻을 바꾸지 않아요. 새로 쓰기는 사용자가 준 재료 밖의 구체 사실을 지어내지 않고 빈자리는 묻거나 비워 둬요.
3. 글만 파일에 담아요. 설명이나 메모가 섞이면 검사가 막아요. 그다음 `check --result <파일> [--draft <파일>] [--material <파일>] [--voice <이름>] [--json]`을 돌려요. 숫자·이름이 달라지거나 베끼면 종료 코드 3이에요. 막힌 곳만 고쳐 다시 돌려요. 재료가 없으면 결과의 숫자·이름이 `확인할 것`으로 나오니 사용자에게 같이 보여 줘요. 목록은 30개까지, 나머지는 `외 N개`예요. 글이 너무 길면 검토 목록과 바뀐 곳은 빠지고 한 줄로 알려요.
4. 결과 글, `바뀐 곳` 목록, 검사 결과를 돌려줘요.
5. 사용자가 고친 글을 주면 `learn --after <고친 글> [--cell <칸>]`을 돌려요. 비교 기준은 마지막 `check`의 결과예요. 칸은 `--cell`, 없으면 마지막 `brief`의 칸이에요. 같은 고침이 두 번 나오면 다음 `brief`의 규칙이 되고, 숫자·이름을 바꾼 고침은 사실 수정이라 문체 규칙으로 올리지 않아요.

## 한계

- 칸 상태는 `충분`, `방향만`, `근거 없음`이에요. 방향만인 칸은 글이 적어서 값이 흔들려요.
- 긴 글을 한 번에 쓰면 분량이 모자라기 쉬워요. 다 쓴 뒤 분량을 확인해요.
- 형태소 분석기가 없어서 사실 대조가 놓치는 이름이 있어요. 조사 없이 쓴 지명(`강남구 주민`)과, 같은 글에 이미 있던 숫자로 바꾼 경우가 그래요. 검토 목록(빠진 문장, 부정 표현, 근사 표현)도 함께 봐요. 옛 표기 글을 오늘 표기로 다듬으면 이름과 숫자가 달라진 것으로 보여 막히기 쉬워요.
- 다른 사람 문체는 흉내까지만 해요. 그 사람 문장을 30자 이상 이어 쓰면 `check`가 막아요. 살아 있는 작가의 이름을 내세운 글의 법적 판단은 사용자 몫이에요.
- 수치가 비슷해도 좋은 글이라는 뜻은 아니에요. 측정은 사용자의 판단을 대신하지 않아요.
