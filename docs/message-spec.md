# 메시지 스펙

채팅 답 하나를 정해진 부품 목록(catalog) 안의 JSON으로 나타내고, 표면마다 그 JSON을 자기 방식으로 그려요. 예전에는 목록, 선택지, `근거:` 줄, 일정, 숫자를 표면마다 글에서 따로 읽어서 새 모양 하나를 넣으려면 여러 곳을 고쳐야 했어요. 이제 모양은 카탈로그에 한 번만 더해요.

방식은 [json-render](https://github.com/vercel-labs/json-render)에서 가져왔어요. 고정된 catalog, 평평한 `{ root, elements }` 트리, 한도예요. 패키지는 쓰지 않아요.

| | `@json-render/core` 0.22 | 직접 구현 |
|---|---|---|
| 설치 크기 | 9.5MB(core 1.2MB, zod 8.1MB) | 0 |
| 페이지 번들 | 102KB, gzip 28.6KB 증가 | 13.5KB, gzip 3.9KB 증가(옛 파서를 지운 뒤) |
| 런타임 의존성 | zod 포함 2개, 저장소의 첫 런타임 의존성 | 0 |

웹 번들은 이미 예산(gzip 500KB) 근처라서 28.6KB를 더 쓸 자리가 없어요. 그 대신 얻는 것(프롬프트 생성, `$state`, `repeat`, 스트리밍)은 답이 한 번에 완성되어 도착하는 채팅에서 쓸 일이 없어요.

## 파일

| 파일 | 하는 일 |
|---|---|
| `hub/message-spec.ts` | catalog, `validateSpec`, `specPlain`, 한도 |
| `hub/message-spec-derive.ts` | 글에서 스펙 만들기(`deriveSpec`), 모델이 쓴 스펙 받기(`resolveSpecFence`) |
| `hub/message-spec-of.ts` | 표면이 보내기 직전에 부르는 `specOf` |
| `hub/gen-message-spec-web.ts` | 위 두 파일을 `web/js/01-message-spec.js`로 생성. 페이지도 같은 코드를 돌려요 |
| `web/js/02-answer-shapes.js` | 웹 렌더러 `specHtml` |
| `hub/spec-discord.ts`, `spec-slack.ts`, `spec-telegram.ts`, `spec-jandi.ts`, `spec-terminal.ts` | 표면별 렌더러 |

## 스펙의 모양

```json
{ "v": 1, "root": "m", "elements": {
  "m": { "type": "Message", "props": {}, "children": ["e0", "e1"] },
  "e0": { "type": "Text", "props": { "text": "일정을 옮겼어요." } },
  "e1": { "type": "Schedule", "props": { "rows": [{ "time": "10:00", "text": "치과" }] } }
} }
```

부품은 `Message` 아래에 한 층으로만 놓여요. 값은 모두 글이고 HTML이 아니에요. 글 안의 굵게, 코드, 링크는 인라인 마크다운으로 쓰고 표면이 자기 표기로 바꿔요.

## 카탈로그

| 부품 | 쓰는 곳 | 글 형태 |
|---|---|---|
| `Status` | 앞머리 상태 표식 | `[done] 첫 줄`, `✅ 첫 줄` |
| `Text` | 문단 | 그대로 |
| `Heading` | 제목 | `## 제목` |
| `Bullets` | 카드가 되지 않는 목록 | `- 항목` |
| `Steps` | 순서 | `1. 항목` |
| `Schedule` | 일정 | `- 10:00 내용` |
| `Facts` | 숫자, 라벨, 바뀐 값 | `- 이름: 값`, `- 이름: 전 → 후` (양쪽 모두 숫자가 있는 24자 이하의 짧은 값일 때만 바뀐 값이에요. 괄호·따옴표·문장부호가 있거나 길면 화살표가 있어도 그냥 값이에요) |
| `Section` | 묶음 보고의 한 부분 | `**제목**` 아래 라벨 줄 |
| `Table` | 표 | 마크다운 표 |
| `Rows` | 항목 목록 | ` ```목록 ` 블록 |
| `Chart` | 그림으로 보면 쉬운 숫자 | ` ```chart ` 블록 (ztd-charts JSON) |
| `Sources` | 출처 링크 | `- 이름: URL` |
| `Quote`, `Meta`, `Evidence` | 인용, 작은 줄, 근거 | `> `, `-# `, `근거: a · b` |
| `Code`, `Rule` | 코드 블록, 구분선 | 펜스, `---` |
| `Choice` | 선택지 표시 | `결정:` 블록 |
| `Files` | 첨부 | `[file] 경로` |

` ```chart ` 블록은 [ztd-charts](https://github.com/Junhan2/ztd-charts) 스펙이에요. 글에서 읽을 때는 JSON 객체인지만 보고, 게이트웨이(`hub/chart.ts`)가 ztd 검증기로 확인한 뒤 웹에는 앱 테마(밝게/어둡게)에 맞는 SVG를, Discord에는 PNG 첨부를 보내요. 데이터는 블록 안에 있어야 하고(`data.url`은 받지 않아요), 검증을 못 넘으면 그림 대신 JSON 코드 블록과 짧은 안내 한 줄이 보여요. 차트 모듈은 처음 그릴 때만 불러와서 게이트웨이 시작 시간과 메모리는 그대로예요. 그림은 `<data dir>/charts`에 해시로 저장하고 30MB를 넘으면 오래된 것부터 지워요.

## 지키는 것

- **검증은 한 곳이에요.** `validateSpec`이 부품 종류, props의 키와 값, 트리, 크기를 봐요. 모르는 키 하나로도 실패하고, 던지지 않고 문제 목록을 돌려줘요.
- **실패해도 답은 남아요.** 글에서 만든 스펙이 검증을 못 넘으면 스펙 없이 글로 나가요. 모델이 쓴 스펙이 틀리면 그 안의 글만 꺼내고, JSON으로도 읽히지 않으면 코드 블록으로 남겨요.
- **HTML이 없어요.** 모든 렌더러가 값을 이스케이프해요. 링크는 http와 https뿐이고, 다른 스킴의 링크가 하나라도 있으면 스펙 전체가 실패해요.
- **동작을 새로 만들 수 없어요.** 카탈로그에 동작 필드가 없어요. 누를 수 있는 것은 오늘 있는 네 가지(선택지 답, 링크, 첨부, 복사)뿐이고 전부 기존 코드를 지나요. 발송 승인이 걸린 메시지는 스펙을 만들지 않아서 `hub/draft-approval.ts`와 승인 카드가 그대로예요.
- **글이 기록이에요.** 저장, 검색, recall, 기억, 알림, 옛 클라이언트는 전부 `text`를 읽어요. `spec`은 답 이벤트에 덧붙는 필드이고 모델에게 다시 가지 않아요. 옛 메시지는 고치지 않아요.
- **대화는 대화로 둬요.** 모양이 없는 답은 스펙이 없어요.
- **상태 표식은 글로 보이지 않아요.** 앞머리 표식은 `[done]`이든 `✅`든 스펙 맨 앞의 `Status`가 되고, 웹은 그 자리에 기존 상태 태그를 그려요. 표식 뒤에 이모지가 또 있으면 표식을 따라요. 모양이 없는 답은 그대로 스펙이 없고, 웹이 글에서 같은 규칙으로 표식을 읽어요. 메신저는 기존처럼 앞머리 이모지만 붙여요.

## 흐름

1. 모델이나 게이트웨이가 글을 써요.
2. `ownerText`가 ` ```dotz-spec ` 펜스를 글 형태로 바꿔요.
3. `emit`이 답이면 앞머리 표식을 읽고(`statedTone`) `deriveSpec`으로 스펙을 만들어 `event.spec`에 넣어요.
4. 웹은 `event.spec`을 그리고, 글만 받는 화면은 같은 코드로 스펙을 만들어 그려요.
5. 메신저는 보내기 직전에 `specOf(text)`로 같은 스펙을 만들어요. 글 형태와 스펙이 서로 왕복되기 때문에 전달 경로에 새 필드가 필요 없어요. 질문 아래 번호 목록은 Discord 버튼이 그 글을 그대로 읽으니까 스펙 없이 글로 나가요.

모델은 지금 스펙을 쓰지 않아요. 카탈로그의 모든 부품이 기존 글 형태에서 나오기 때문에 JSON을 쓰게 하면 토큰만 늘어요. `MODE.md`에도 스펙 이야기가 없어요. 펜스 입구는 글로 표현할 수 없는 부품이 생길 때를 위한 자리이고, 그때 검증을 다시 만들 필요가 없어요.

## 표면이 모자랄 때

렌더러는 부품 일부만 알아도 돼요. 렌더러가 모르는 부품은 그 부품의 글 형태로 나가요. 표면 한도는 부품별로 낮춰요.

| 표면 | 그리는 방식 | 한도를 넘으면 |
|---|---|---|
| 웹 | 카드와 행 | 없음 |
| Discord | 본문 글, `-# `, `[이름](<URL>)` | 1,900자마다 나누고 행이나 펜스 안에서는 자르지 않아요 |
| Slack | Block Kit, `text`는 그대로 | 부품을 글 섹션으로 낮추고, 그래도 넘으면 `text`만 보내요 |
| Telegram | HTML 모드 | 4,096자마다 부품 경계에서 나눠요. 파싱 오류면 평문으로 다시 보내요 |
| Jandi, 그 밖의 메신저 | 부품별 글 줄 | 기존 나누기 |
| 터미널 | ANSI | `NO_COLOR`면 글자만 |

## 부품 추가하기

1. `hub/message-spec.ts`의 `CATALOG`에 부품을 더해요. `props`와 `plain` 둘 다 필수예요.
2. 글에서 읽을 수 있으면 `hub/message-spec-derive.ts`에 읽는 규칙을 더해요.
3. `bun hub/gen-message-spec-web.ts`로 페이지 파일을 다시 만들어요.
4. `web/js/02-answer-shapes.js`의 렌더러 표에 HTML을 더해요.

메신저 렌더러는 고치지 않아도 글 형태로 나가요. 더 잘 그리고 싶은 표면만 항목을 더해요.

## 영향

최근 답 1,035건(10월 31일부터 일주일)으로 쟀어요. 그중 34%인 356건이 스펙을 가져요. 나머지는 모양이 없는 대화예요.

- **토큰:** 답마다 0이에요. 게이트웨이가 글에서 만들고 모델에게 스펙을 보내지 않으며, `MODE.md`도 그대로예요. 모델이 JSON을 직접 쓰면 스펙이 있는 답 하나에 약 90토큰, 1.24배가 들어서 쓰지 않아요.
- **메모리:** 스펙이 있는 답 하나에 평균 2KB, 글의 1.21배예요. 이벤트 300개를 들고 있는 링에 최대 230KB가 늘어요. 운영 메모리 173-355MB에 비하면 0.1% 안쪽이에요. `outbox.jsonl`은 일주일에 약 700KB 늘어요.
- **속도:** `deriveSpec`은 중앙값 0.005ms, p95 0.05ms, 최대 1.2ms예요.
- **화면:** 옛 코드와 새 코드로 답 1,035건을 세 가지 방식으로 그려 비교했을 때 달라진 것이 없어요. 390px, 1280px의 라이트와 다크 화면도 픽셀까지 같아요.

## OmO와 비교

OmO에는 이런 부품 목록이 없어요. 답은 마크다운이고, 더 필요하면 모델이 HTML 한 장을 직접 만들어(`visualize`, `show_html_page`) 린트를 거쳐 보여 줘요. 표현력은 넓지만 토큰이 많이 들고 메신저에서 쓸 수 없어요. dotz는 답이 여러 메신저로 나가고 모델 토큰을 늘리지 않아야 해서 카탈로그가 맞아요.
