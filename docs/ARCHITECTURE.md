# Module map

Paths only; each file's header comment says what it does. Tests sit next to their module as `*.test.ts`.

## Entry points

- `hub/main.ts` gateway process (startup, timers, shutdown, restart gate)
- `hub/dotz-command.ts` the `dotz` terminal command (loopback entry, any web.access mode); `hub/web-login-cli.ts` is what it runs
- `setup.ts` + `onboard/` install wizard (`harness.ts`, `service.ts`, `tailscale.ts`, `aside.ts`, `discord.ts`, `permissions.ts`)
- `firstrun/` first-run web onboarding between hub and onboard: the marker (`first-run.ts`, `first-run-boot.ts`), the gate and its jobs (`setup-gate.ts`, `setup-jobs.ts`, `setup-state.ts`, `setup-term.ts`, `setup-apply.ts`) and the shared answers/apply/scan/exec code; it may import hub and onboard, and only `hub/main.ts`, `hub/routes.ts`, `hub/routes-settings.ts` and `setup.ts` import it
- `extension/index.ts` agent-side extension (`guard.ts`, `guard-config.ts`, `harness-tools.ts`, `output-cap.ts`, `owner-values.ts`, `task-cap.ts`, `task-cap-grow.ts`, `compact-kept.ts`, `schema.ts`, `token-audit.ts`, `connect-view.ts` (the `dotz_connect` tool's plain-text view of a messenger connection))

## Gateway core

- config and process: `hub/config.ts`, `hub/statefile.ts` (reads a JSON state file: absent vs unreadable, which is set aside), `hub/opener.ts` (browser opener, WSL detection), `hub/lock.ts`, `hub/file-lock.ts` (the lock directory OmO's auth.json writers take), `hub/shutdown.ts`, `hub/restart.ts`, `hub/live-guard.ts`, `hub/public-scrub.ts` (what may leave an install for public GitHub: the agent post check and the release-note scrub), `hub/release-note.ts` (the note of a GitHub Release, from commit bodies), `hub/release-gate.ts` (the full suite on the head of origin/main, run detached across watch ticks from its own clone, before a release slot dispatches), `hub/release-sign.ts` (the release signing key path, SSH-signed annotated release tags and their check against `release-signers`, the unsigned-transition rule), `hub/systemdeny.ts`
- HTTP: `hub/routes.ts` -> `hub/routes-apps.ts` (apps, integrations, reply drafts) -> `hub/routes-notices.ts` (notices) and further `hub/routes-settings.ts` -> `hub/routes-lanes.ts`, the conversation list and mail routes `hub/routes-mail.ts`, the send routes (message, queue, send) `hub/routes-send.ts`, the conversation list's full mail card `hub/conversations-mail-card.ts`, helpers `hub/routes-util.ts`, entry check (own Host names, tailnet identity only via tailscale serve, no cross-site writes) `hub/entry-check.ts`, owner answers sealed by the gateway (HMAC) so only they approve a send `hub/approval-seal.ts`, web assets `hub/webapp.ts`, `hub/compress.ts`, files `hub/files.ts`, `hub/upload-stream.ts`
- message flow: inbound `hub/intake.ts`, outbound `hub/outbound.ts` (a session's post into another conversation needs a named reason, else it lands in its own: `hub/conv-guard.ts`; a model-written question that stops to ask about going on at a low usage limit steers the orchestrator: `hub/limit-ask.ts`), send ledger `hub/sendlog.ts`, prompt queue `hub/prompts.ts` (its types and limits `hub/prompts-model.ts`), web queue `hub/queue.ts`, background workers `hub/bgwork.ts` (the files, commits and links a finished report names, shown as chips on its row: `hub/result-refs.ts`; the files /api/file serves because a chip names them: `hub/listed-files.ts`), event bus `hub/events.ts`, the one strip that keeps the gateway's added prompt text (the work-channel note, the language line) off every screen `hub/gateway-added.ts`
- request tracking: a worker is linked to its owner message at spawn (`hub/prompts.ts` WorkLink, `*-links.json` beside `pending.json`, survives a restart); each spawned worker gets its own line, its result answers exactly that message, a short todo-closing last message never replaces its report (`hub/bgwork.ts` reportOf), and `hub/waitcheck.ts` wakes the session once, bounded and with no model call before that, when a request stays open for 2 minutes with nothing running
- orchestrator: `hub/orchestrator.ts` (start prompt, handover and status record `hub/orchestrator-parts.ts`, the stuck-turn watch shared with lanes `hub/stuck.ts`), `hub/context.ts`, `hub/compact-instructions.ts` (what the orchestrator's summary must keep and drop), `hub/fallback.ts`, `hub/limit-alert.ts`, `hub/outlang.ts`, `hub/tone.ts`
- text: `hub/i18n.ts` (+ catalogs `hub/i18n-en.ts`, `hub/i18n-ko.ts`), `hub/language.ts`, `hub/prompt-budget.ts`
- message shapes: `hub/message-spec.ts` (the fixed component catalog and its validator), `hub/message-spec-derive.ts` (text to spec: the one reader of an answer's shapes, and the dotz-spec fence), `hub/gen-message-spec-web.ts` (writes `web/js/01-message-spec.js`, the page's copy of both; `web/js/02-answer-shapes.js` draws the spec)
- in-message charts: `hub/chart.ts` (a ```chart fence of ztd-charts JSON checked and drawn on demand: SVG in both themes for the web via `POST /api/chart`, a PNG attachment for Discord; ztd-charts and resvg load lazily, never on the start path; drawings cached under `<data dir>/charts`), drawn on the page by `web/js/02-chart.js`.

- outside commands: `hub/run-limited.ts` (one way to run a command with a time limit: the child leads its own process group, the limit kills the whole group, the result tells a timeout (code 124, `timedOut`) from a failure; a command that cannot start is code 127; used by the tailscale, mail, onboarding, provider-login, aside and send-CLI calls)
