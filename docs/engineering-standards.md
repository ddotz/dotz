속도, 안정성, 기술부채, 코드 꼬임, 중복을 재는 기준이에요. 값은 2026-11-05에 main(`1d03f655` 기준)에서 잰 수치에서 정했어요. 이 머신은 측정 내내 다른 세션이 돌아 부하 평균이 8-50이었으니, 시간 값은 바쁜 맥북 기준으로 읽어요.

강제 방식은 `hub/design-rules-web.test.ts`와 같아요. 코드로 잴 수 있는 기준은 `hub/engineering-rules.test.ts`가 지켜요. 지금 위반은 개수 상한으로 동결해서 새 위반만 실패해요. 고치면 상한을 내리고, 변경을 통과시키려고 올리지 않아요. 지금 값은 `bun hub/engineering-rules.ts`로 봐요.

## 측정으로 지키는 기준

게이트로 걸기에는 흔들리는 값이에요. 크게 바꾸는 변경 전후로 재고, 기준을 넘으면 그 변경에서 원인을 찾아요.

| 항목 | 기준값 | 현재값 | 확인 방법 |
|---|---|---|---|
| 전체 시험 시간 | `--parallel=4`로 3분 이하, 실패 0 | 4,274개 시험. `--parallel=4` 3회 130-173초, 실패 0·1·0건. 코어 수(10) 5회 153-275초, 실패 5-91건 | `bun run test` |
| 재시작 중단 시간 | 중앙값 3초 이하 | 중앙값 2.27초, 248회, 가장 긴 정상 값 5.3초 | `hub.log`의 `gateway restart`에서 `hub listening`까지 |
| 냉시동 | 4초 이하 | 1.9-3.9초(5회, 부하 40대) | `hub/update-smoke.ts`와 같은 임시 폴더로 `/api/health` 응답까지 |
| 게이트웨이 메모리 | 시작 직후 80MB, 운영 400MB 이하 | 시작 직후 52-63MB, 운영 173-355MB(72분 사이 변동) | `ps -o rss=` |

## 코드로 못 잡는 약속

- 새 기능 전에 같은 일을 하는 기능을 찾아요. `docs/ARCHITECTURE.md`를 먼저 보고, 없으면 같은 데이터를 읽는 화면과 같은 동작을 끝내는 경로를 `grep`해요. 두 번째 경로를 만들면 첫 경로를 지우거나, 왜 둘이어야 하는지 브리프에 적어요.
- 보내기 경로는 하나의 확인을 지나요. 승인 판정은 `hub/draft-approval.ts`, 중복 발송 방지는 `claimSend`예요. 카카오톡의 따로 있는 판정은 알려진 예외예요.
- 오류는 처리하거나, 기록하거나, 왜 무시해도 되는지 주석을 남겨요. 사용자 작업을 잃는 실패는 삼키지 않아요.
- 시험은 혼자 돌 때와 `--parallel=4`에서 둘 다 통과해야 해요. 시간을 재는 시험은 시간 자체가 동작일 때만 쓰고, 나머지는 호출 횟수나 사건을 세요.
