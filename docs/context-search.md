# 맥락 검색

"그때 그거"처럼 막연한 말로 지난 대화를 찾는 도구입니다. 평소 프롬프트에는 아무것도 더하지 않고, 찾을 때만 씁니다. 대화 내용은 이 컴퓨터를 떠나지 않고, 색인과 검색에 모델 호출을 쓰지 않습니다. 다른 컴퓨터의 대화는 아직 찾지 못합니다.

## 쓰는 법

세션은 `dotz_recall`을 씁니다. 오케스트레이터, 대화 세션, 레인, 워커 모두 같습니다. 지연 도구라서 `tool_search`로 찾고, 프롬프트에는 스키마가 들어가지 않습니다. 막연한 말을 푸는 일은 묻는 쪽 모델이 합니다.

1. 지금 맥락으로 시기, 프로젝트, 주제를 추립니다.
2. `query`에 뜻을 쉬운 말로 쓰고, `also`에 원래 대화에 있었을 법한 다른 표현을 2~3개 씁니다. `after`, `before`는 실제 시간 단서가 있을 때만 여유를 두고 씁니다.
3. 결과의 id를 `open`으로 열어 원문을 읽고 답합니다. 맞는 것이 없으면 못 찾았다고 말합니다.

명령줄도 같습니다: `bun hub/recall-cli.ts search <질문> [--also x] [--after 날짜] [--before 날짜] [--project p] [--keyword]`, `open <id>`, `status`, `refresh`.

## 구조

- `hub/recall-extract.ts`: 세션 파일에서 사람 말과 답을 짝으로 뽑습니다. 도구 출력과 시스템 프롬프트 덩어리는 뺍니다.
- `hub/recall-index.ts`: `<data>/recall/index.db`(`bun:sqlite`, FTS5)에 시각, 대화방, 프로젝트와 함께 저장합니다. 바이트 위치로 이어서 읽어 새 줄만 색인합니다.
- `hub/recall-embed.ts`: 첫 `refresh`가 런타임과 모델을 `<data>/recall`에 받습니다. 켜는 단계는 없습니다. 버전을 고정하고, 설치 스크립트를 돌리지 않고, 모델은 sha256을 확인합니다. 실패하면 6시간 뒤 다시 시도합니다.
- `hub/recall-search.ts`: 표현마다 키워드 목록과 벡터 목록을 만들어 순위 융합으로 합칩니다(k 20, 벡터 가중치 2). `sqlite-vec`은 Bun의 SQLite가 확장을 막아서 못 쓰고, 벡터는 BLOB으로 두고 전수 비교합니다. 2천 건에서 충분히 빠릅니다.
- `hub/recall-rerank.ts`: 합친 순서의 상위 30개를 작은 교차 인코더가 질문과 함께 읽어 다시 줄 세웁니다. 임베딩 모델과 같은 방식으로 받고, 없거나 실패하면 합친 순서를 그대로 씁니다.
- `hub/recall-idle.ts`: 게이트웨이가 5분마다 `refresh --budget-ms 20000`을 낮은 우선순위 자식 프로세스로 띄웁니다. 세션이 일하는 중이면 건너뛰되, 마지막 실행 뒤 1시간이 지나면 돌립니다. 게이트웨이 프로세스는 모델도 색인도 열지 않습니다.
- `extension/recall-tool.ts`: CLI를 자식 프로세스로 실행하는 `dotz_recall`입니다.

뜻 검색을 못 쓰는 환경(지원하지 않는 플랫폼, 내려받기 실패, 벡터가 아직 없을 때)에서는 키워드 검색으로 돌아가고 결과 첫 줄에 `(keyword only)`를 적습니다. 첨부 보관 기간은 건드리지 않습니다. 색인 폴더는 0700이고 대화 내용이 들어 있어서 저장소 밖에 둡니다.

## 모델과 런타임을 고른 이유

임베딩은 `jhgan/ko-sroberta-multitask`의 8비트 ONNX(107MB, 768차원, Apache-2.0)를 `onnxruntime-node`로 돌립니다.

런타임은 네이티브가 WASM보다 약 8배 빠르고 메모리는 적었습니다(같은 e5-small 기준, 짧은 글 5ms 대 34ms, 최대 메모리 601MB 대 888MB).

모델은 실제 대화 2천 쌍, 막연한 질문 25개(튜닝셋)로 비교했습니다. 전체 임베딩의 시간과 최대 메모리도 같이 쟀습니다.

| 모델 | 뜻+키워드 상위 5 | 뜻만 상위 5 | 전체 임베딩 | 최대 메모리 | 크기 | 라이선스 |
| --- | --- | --- | --- | --- | --- | --- |
| ko-sroberta-multitask | 23/25 | 17/25 | 281초 | 422MB | 111MB | Apache-2.0 |
| embeddinggemma q4 | 23/25 | 20/25 | 502초 | 677MB | 197MB | Gemma 약관 |
| 다국어 e5-small | 21/25 | 16/25 | 114초 | 721MB | 118MB | MIT |
| 다국어 MiniLM | 탈락(합성 10문항 1위 적중 1개) | | | | | |

재순위는 `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`의 8비트 ONNX입니다. 49문항 5겹 교차검증에서 상위 5가 40개에서 44개로 늘었고, 다른 후보 gte는 42개에 최대 메모리가 약 1.4GB였습니다. 가중치와 k 360조합은 나아지지 않아서 넣지 않았습니다.

젬마는 1위 적중이 15개로 ko-sroberta의 13개보다 조금 낫지만 상위 5는 같고, 두 배 가까이 느리고 크며 메모리도 더 씁니다. 재배포 약관도 따로 있습니다. 그래서 ko-sroberta를 골랐습니다. 벡터는 쌍마다 하나(사람 말 앞 500자 + 답 앞 900자)이고, 더 잘게 나눠도 튜닝셋 점수가 나아지지 않았습니다.

## 측정

M2 Pro, 2026-11-06, 대화 1992쌍(세션 590개, 1.3GB). 게이트웨이 값은 `hub/test/load-qa`의 대규모 테스트 게이트웨이입니다.

- 처음 전체 색인: 키워드 2.7초(최대 222MB), 임베딩은 조각 하나(20초)에 239쌍이라 쉼 때 돌면 약 45분에 끝납니다. 자식 프로세스 최대 331MB, CPU 2코어(nice 15).
- 증분 색인: 새 대화 두세 건에 0.3초, 265MB.
- 검색 한 번: 표현 3개에 재순위까지 1.2초, 최대 846~889MB. 잠깐 뜨는 자식 프로세스라 끝나면 메모리를 돌려줍니다.
- 디스크: 색인 31MB, 런타임 90MB, 임베딩 모델 107MB, 재순위 모델 129MB.
- 게이트웨이 영향: 색인 조각이 도는 20초 동안 `/api/state` p50 3.9ms, p95 5.2ms로 직전(p50 4.0ms, p95 20ms)보다 나빠지지 않았고 게이트웨이 CPU도 p50 3.7%였습니다. 시작 5분 뒤 실제 타이머가 돈 뒤 RSS 296MB, p50 16.5ms는 맥락 검색 코드가 없는 기준 커밋의 같은 시점(299MB, 15.7ms)과 같은 범위입니다.
- 프롬프트: 도구를 뺀 실제 세션과 입력 토큰이 33,108로 같습니다. 도구를 처음 찾아 쓰는 세션에서만 스키마가 들어갑니다.

## 평가

공식 판정은 저장소 밖 `/tmp/context-search/eval.md`에 있습니다. 평가셋에 개인 대화가 들어 있어서 저장소에는 넣지 않습니다. 독립 서브에이전트가 질문 49개와 정답을 만들고, 절반을 튜닝에 쓰지 않고 남겨 한 번 쟀습니다.

1차(2026-11-06, 재순위 없음)는 FAIL이었습니다. 남겨 둔 24개에서 상위 5가 맥락 검색 17/24, 같은 인자 단어 검색 17/24였습니다.

2차는 PASS입니다. 재순위를 넣어 코드를 고정한 뒤 새로 만든 43개를 한 번 쟀습니다. 상위 5는 맥락 검색 38/43(88.4%), 같은 인자 단어 검색 35/43(81.4%), 질문 그대로의 단어 검색 31/43(72.1%)이고, 1위 적중은 31, 23, 18개입니다.

이 수치의 한계: 43개 중 실제 되짚은 말은 2개뿐이고 나머지는 합성 문항입니다. 1차 실제 문항 14개(이제 튜닝 자료)에서는 맥락 검색 9개, 같은 인자 단어 검색 10개였습니다. 실제 사용에서 얼마나 맞히는지는 아직 충분히 재지 못했습니다.
